# DISC-002 — 주행 실패 진단과 블랙박스 운용 리플레이

기준일: 2026-09-21 (KST). 이 문서는 선행 진단·기획 이력과 남은 확장 제안이다.
같은 날 후속 요청으로 PLAN-13과 재현된 트래픽 결함의 동시 구현을 승인받았다.
구현된 동작은 [FMS 블랙박스](../../fms/current/blackbox.md),
[웹 블랙박스](../../web/current/blackbox.md), [로봇 주행](../../robot/current/navigation.md)이 정본이다.
아래 ‘미승인/제안’ 표현과 실패 분석은 **구현 전 검토 당시**의 기록이며 현재 실행 동작이 아니다.

아직 구현하지 않은 제안: 독립 export/보존 고정, 전역 용량·자산 GC, 분산 시계/빌드 추적,
로봇별 운용 구간 lane·operation 검색, 리플레이 중 다른 맵으로 동일 시각 전환,
결정론적 알고리즘 재실행. 새 착수 지시로 해석하지 않는다.

### 최초 검토 기록

당시 상태: 사용자 선행 검토용 제안. 구현 미승인.
후속 요청으로 리플레이 모드의 라이브 이벤트 격리 기획과 카드 등록을 승인받았다.
주행 수정·기록기 등 전체 구현 착수 승인을 뜻하지 않는다.
관련 기획 카드: [PLAN-13](http://192.168.0.172:3456/tasks/30) · FMS/planning · To Do.
이번 검토에서는 실행 코드, PM2 프로세스, 운용 상태를 변경하지 않았다.
운영 로그·DB를 읽고 Colyseus 상태를 관측했으며, 별도 로컬 프로세스에서 계산·컨트롤러만 재현했다.

## 요청과 범위

- 테스트 위치 지정 후 두 로봇의 빈번한 주행 실패 원인을 분석하고 수정 범위를 정한다.
- 운용 요청부터 프로토콜 송수신, 로봇 판단, 트래픽 제어, 결과까지 operation ID로 연결한다.
- 파일 로그로 기록하고, 선택한 맵과 가로 타임라인의 시간 범위를 기준으로 재생하는
  독립 기능을 **블랙박스**로 정의한다.
- 지도 로봇 라벨에 이름·상태·주행 모드를 표시한다.
- 사용자 최신 요청은 **검토 먼저**다. 아래 설계는 착수 지시나 완료된 기능이 아니다.

## 현재 실패에서 확인한 사실

### 1. 정상 주행 중 불필요한 재계획과 HOLD 전환 — 재현됨

`virtual-robot/src/controller.ts`의 `setPeerLocalPlans()`는 장애물이 없는 경우에도
목적지에 아직 도착하지 않았다는 조건만으로 `retryTrueGoal()`을 호출한다.
목적지까지 이미 온전한 경로가 있는 정상 주행도 이 조건에 해당한다.
`retryTrueGoal()`은 재계획 주기 800ms 안의 호출에서 기존 주행을 HOLD로 바꾼다.
주변 로봇 경로는 FMS에서 최대 10Hz로 전달하므로 같은 경로의 재계획과 HOLD가 반복될 수 있다.

운영 로봇에 명령을 보내지 않는 로컬 재현:

1. Yard 컨트롤러를 (240,520)에서 (300,520)으로 이동하도록 초기화.
2. 경로 끝점이 (300,520)인 것을 확인.
3. 빈 주변 로봇 목록을 한 번 전달 → `running / v1-goal-retry`로 재계획.
4. 곧바로 빈 목록을 다시 전달 → `HOLD`로 전환.

PM2 `fms-robot-1-out.log`에는 09:57~10:02에 거의 동일한 340~341점 경로를
약 2초 간격으로 다시 계획하는 기록이 반복된다.

수정 제안: 실제 경로 차단·유효성 변경·짧게 끝난 경로의 목표 재시도만 재계획한다.
단순 주기 제한은 유효한 경로의 진행 상태를 바꾸지 않는다.
계획 입력의 revision과 시작 원인을 기록하고 동일 입력의 중복 요청을 합친다.

### 2. 동기식 경로 계산이 통신·주행 처리를 함께 막음 — 지연 재현, timeout 연관 유력

`shared/planner.ts`의 A*와 경로 단순화는 로봇의 gRPC 수신·50ms 주행 타이머와 같은
스레드에서 동기 실행된다. 현재 Large Lab의 실제 prefer(0.4)·avoid(3) 존을 읽어,
(3642,2305) → (2847.8924,2498.6671) 경로를 별도 프로세스에서 계산했다.

- 경로 341점, 계산 약 **2452ms**.
- 10ms 후 실행하도록 예약한 타이머가 약 **2456ms** 후 실행됨.
- 실제 상대 로봇·경로 장애물을 포함하지 않은 측정이며 성능 보증값은 아니다.

기존 로그에는 09:52:17~09:55:40에 heartbeat timeout이 robot-1에서 2회,
robot-2에서 13회 기록되어 있고 FMS의 단절·재등록 시각과 대응한다.
현재 timeout은 3000ms다. 재접속은 새 세션 동기화를 수행하면서 이전 운용 명령을 정리한다.
관측 시 robot-2의 마지막 명령은 `interrupted / control synchronization required`였다.

반복 동기 계산에 의한 통신 지연은 유력한 원인이지만, 당시 명령별 목표·계산 시간·수신 지연이
없어 모든 timeout을 개별적으로 인과 확정할 수는 없다. 로그가 담지 않은 과거 실패 원인도 미확정이다.

수정 제안: 경로 계산을 Worker로 분리하고 취소·시간 예산·동시 실행 수를 제한한다.
결과 적용 시 operation ID, session ID, control epoch, 맵/환경 revision을 확인해
위치 지정·맵 전환·운영 제외 이전의 계산 결과가 적용되지 않게 한다.
계산 중 안전 상태를 명시하고 통신·텔레메트리를 지속한다.

### 3. 대형 맵의 장애물 마스크 반복 할당 — 코드로 확인한 부하 요인

주변 로봇 경로 갱신마다 `applyMergedObstacles()`가 `rasterizeObstacles()`를 호출한다.
후자는 맵 전체 `Uint8Array(MAP_WIDTH * MAP_HEIGHT)`를 새로 만든다.
Large Lab에서는 호출당 100,000,000바이트(약 100MB)이며, 최대 10Hz 갱신 시
로봇 하나당 초당 약 1GB의 배열 할당 요청이 가능하다. 실제 물리 메모리 쓰기량과는 구분한다.
관측 시 PM2 robot-1 RSS는 약 1.1GB였다. 이것만으로 메모리 누수라고 판정하지 않는다.

수정 제안: 주변 장애물 변경 감지, 재사용 버퍼/변경 영역 갱신 또는 타일 기반 마스크를 검토한다.
맵 전환 시 이전 마스크와 계획 컨텍스트를 확실히 폐기한다.

### 4. 테스트 위치 지정 확인과 관측 정보 — 별도 결함 후보

운영 제외 중 주변 로봇 경로·텔레포터 제약 전송은 `writeOperational()`의 제어 guard에 막힌다.
로봇의 위치 지정 검사는 기존 peer/teleporter 정보를 참조하므로 오래된 정보가 거절에 영향을 줄 수 있다.
현재 위치와 같은 좌표를 요청하면, 로봇이 요청을 거절해도 서버가 같은 epoch의 일반 pose만 보고
성공으로 판단할 수 있다. 이전 검증 시각의 로봇 로그에 `rejected locally infeasible pose override`가
있는데 runtime audit에는 같은 request ID의 `pose_override_pose_confirmed`가 남아 있다.

이전 E2E는 동일 좌표 지정으로 성공을 확인해 이 문제를 검출하지 못했다.
이번 사용자의 서로 다른 새 좌표 지정은 두 로봇 모두 audit에서 확인됐으므로,
이번 주행 중단 전체를 위치 지정 실패로 단정하지 않는다.

수정 제안: 로봇에서 request ID별 명시적 적용/거절 ACK와 구체적인 reason code를 보낸다.
서버는 적용 ACK와 적용 후 최신 pose를 모두 확인해야 성공 처리한다.
운영 제외 중에도 위치 검증에 필요한 최신 관측 정보를 공급하고, 계획용 미래 경로와
현재 몸체의 충돌 검사를 구분한다. 위치 지정 뒤 disabled 유지 정책은 그대로 적용한다.

## 블랙박스의 데이터 계약 제안

### 운용 ID와 상관관계

운용 요청을 받는 즉시 `operationId`(UUID)를 부여한다. 사전 검증에서 거부된 요청도 기록한다.
move, dock, cancel, 테스트 위치 지정, 운영 제외/재개, 점유 해제, teleporter를 포함한다.
`clientRequestId`로 요청 재전송을 판별하고 같은 요청의 ID를 유지한다.
기존 `commandId`, `transferId`, `requestId`, `sessionId`, `controlEpoch`를 별도 필드로 연결한다.
한 텔레포터 운용의 접근·이전·자동 이탈은 같은 operation 아래 하위 단계로 기록한다.
취소·운영 제외는 자체 operation을 갖고 영향을 받은 operation을 참조한다.
여러 로봇의 트래픽 판단은 `relatedOperationIds`, `robotIds`, `resourceRefs`로 연결한다.

이벤트 공통 필드 제안:

```text
schemaVersion, eventId, operationId?, parentEventId?, relatedOperationIds[]
source, processBootId, sequence, timestampUtc, monotonicMs, receivedAtUtc?
mapId, robotId?, commandId?, transferId?, sessionId?, controlEpoch?
eventType, direction?, outcome?, reasonCode?, payload
mapRevision, environmentRevision, buildId
```

프로세스 내부 순서는 boot ID + sequence로 보장하고, 송수신은 message ID/인과 참조로 연결한다.
서로 다른 프로세스의 monotonic clock은 직접 비교하지 않는다. 시계 차이·수집 지연을 표시한다.
프로토콜을 확장할 경우 서버·로봇 버전과 호환 정책을 함께 변경한다.

기존 PM2 stdout과 SQLite runtime audit, 마지막 위치 복구 journal은 블랙박스의 대체물이 아니다.
특히 복구 journal은 최신 상태를 덮어쓰며 과거의 경로·환경·판단을 보존하지 않는다.

### 파일 구조와 기록기

제안 루트: `FMS_DATA_ROOT/blackbox/`.

```text
blackbox/
  assets/<content-hash>/...                  # 당시 맵·정의·설정
  streams/<date>/<source>/<boot-id>/
    segment-000001.events.ndjson            # 변경 불가 원본, 프로세스별 단일 writer
    segment-000001.index.json               # 시간·맵·operation별 offset
    checkpoint-<sequence>.json              # 시작/주기/환경 변경 시 전체 상태
  operations/<operation-id>/
    manifest.json                          # 결과·기간·참여 맵/로봇·원본 이벤트 참조
  exports/<operation-id-or-range>/
    replay.ndjson                          # 선택 운용 또는 시간 범위의 통합 로그
    manifest.json                          # 초기 상태·자산·기록 공백 정보
```

원본 파일은 각 프로세스가 자신만의 stream에 기록하며 여러 프로세스가 같은 파일에 append하지 않는다.
인덱스·operation manifest는 원본에서 재생성 가능하게 하고, 단일 인덱서가 갱신한다.
operation별 조회/내보내기에는 해당 명령 외에도 당시 주변 로봇·환경·트래픽 맥락을 포함한다.
맵 전체 이벤트는 명령이 없는 idle/disabled/offline 로봇까지 기록해야 다른 로봇의 실패를 해석할 수 있다.

비동기 배치 기록과 bounded queue를 사용한다. 핵심 이벤트는 전건 기록하고, pose/local-plan 원본도
프로토콜 주기(현재 20Hz)로 수집하되 불변 payload는 content hash로 중복 저장을 줄인다.
heartbeat 정상 반복은 요약 가능하지만 timeout과 경계 이벤트는 전건 남긴다.
디스크 포화·기록 큐 포화는 주행 스레드를 막지 않고 `recording_gap`과 recorder 상태로 노출한다.
flush/fsync 정책과 마지막 flush 이후 손실 가능 구간을 명시하고, 잘린 마지막 NDJSON 행은 복구 시 격리한다.

초기 운영 기본값 제안: 7일 또는 총 10GiB 중 먼저 도달하는 한도로 보존, 닫힌 segment 압축,
보존 고정한 장애 구간은 별도 관리. 실제 기록량을 측정해 조정하며 무손실·무제한 보존을 약속하지 않는다.
PM2로 실행하며 별도 systemd 데몬은 추가하지 않는다.

## 리플레이 UI와 동작

현재 선택한 맵에 대해 화면 하단 가로 타임라인을 제공한다. 최근 24시간 기록 중 운용 명령,
오류 상태로의 변화, 강제 상태전환 등 운용환경에 영향을 주는 사건에서 시작·끝 이벤트를 선택한다.
로봇별 운용 구간 막대와 사건 마커/목록을 제공하고, 범위 핸들은 선택 가능한 사건에 스냅한다.
진행 중 명령은 열린 구간, 사전 거절은 순간 마커로 나타낸다. operation 검색으로 후보를 좁힐 수 있다.
정상 pose/heartbeat는 경계 선택 후보가 아니지만, 선택한 두 사건 사이의 실제 재생에는
맵 재현에 필요한 위치·경로·주변 로봇·점유·환경 기록 전체를 포함한다. 24시간은 선택 기간이며 보존 기간과 별개다.

- 재생/일시정지, 배속(0.25/1/2/4배), 커서 이동, 이전/다음 이벤트 이동.
- 선택 구간의 로봇 pose·이름·상태, 경로, 존/텔레포터 점유·대기열·트래픽 신호 재생.
- 이벤트 선택 시 원인·operation ID·프로토콜 송수신·해당 로봇 판단 상세 표시.
- 선택 시간 직전 checkpoint에 이후 이벤트를 적용해 시작 상태를 복원한다.
- 자산이 바뀐 구간은 기록 당시 자산을 사용한다. 자산·기록이 없으면 공백을 표시한다.
- 지도 전환 시 소유권 이전 이벤트로 입장/퇴장을 표현한다. 관련 다른 맵으로 같은 시각에 이동 가능하다.
- 리플레이 상태 저장소와 라이브 상태 저장소를 분리하고, 리플레이 중 운용 명령 전송을 차단한다.
- 가능하면 기존 UI 갱신 로직은 변경하지 않고 라이브/블랙박스 이벤트 채널 소스만 교체한다.
  블랙박스 모드에서는 그 채널의 이벤트만 화면에 적용한다. 라이브 데이터 수집·캐시 중단은 필수 조건이 아니다.
  서버·로봇 운용과 파일 기록은 유지한다.
- 리플레이 화면 전체는 기록 이벤트·당시 자산·재생 시계만 사용한다. 라이브 상태/ACK/재접속/지연된
  비동기 응답이 화면을 변경하지 못하게 한다. 기록 누락·로딩 실패도 라이브 데이터로 보충하지 않는다.
- 텔레포트·테스트 위치 지정·단절·기록 공백은 보간하지 않는다. 일반 pose 사이의 시각 보간은
  실제 측정값과 구분하고, 정확한 이벤트 스텝에서는 원본 값을 사용한다.

첫 버전의 replay는 **기록 당시 상태와 사건의 시각적 재생**이다.
알고리즘을 다시 실행해 같은 결정을 재현하는 실험은 별도 후속 범위이며,
결정론적 재실행에는 입력 순서·시간·난수·빌드·설정까지 통제해야 한다.
지금까지의 과거 운용은 원본 정보가 부족하므로 완전한 블랙박스 리플레이로 소급 복원할 수 없다.

제안 컴포넌트 경계: 공통 이벤트 계약/기록기, FMS·로봇 계측, 파일 인덱서/조회,
LiveEventChannel/BlackboxEventChannel, 공통 이벤트 적용기·화면 상태/재생 시계,
BlackboxTimeline/이벤트 상세, 공통 맵 렌더러.
파일 조회·리플레이는 운용 명령을 재전송하지 않는다.

2026-09-21 사용자 추가 요구: 웹의 리플레이 모드에는 현재 로봇 이벤트를 적용하지 않고
블랙박스 기록만 적용한다. 상태 소스, 모드 전환, 전송 차단과 검증 기준은
[웹 리플레이 격리 상세 기획](../../web/backlog/blackbox-replay-mode.md)에서 관리한다.
같은 날 최종 정정: ‘라이브 모니터링 데이터 갱신 중단’ 해석을 철회하고, 기존 UI 갱신 로직을
최대한 유지한 채 블랙박스 채널만 화면 소스로 연결하는 것으로 명확히 했다. 최근 24시간의
운용 영향 이벤트에서 시작·끝을 선택하는 조건도 추가했다. 구현 착수 승인은 별도다.

## 지도 로봇 라벨

현재 `drawRobotRuntime()`는 `유휴 · 정지` 등 상태만 표시하고 이름·주행 모드가 없다.
`{표시이름 또는 robotId}_{상태}_{주행모드}`로 표시한다. 예: `robot-1_주행중_자유주행`.
오프라인/운영 제외는 별도 배지로 표시하고, 오류·대기는 reason을 상세 패널에 연결한다.
현재 Robot schema에 name 필드가 없으므로 초기 이름은 robotId로 대체한다.
별도 이름 변경 UI는 이 요청의 필수 범위로 가정하지 않는다.
폰트는 화면 픽셀 크기를 유지하고 겹칠 때 선택 로봇 라벨을 우선한다.
라이브와 블랙박스가 같은 라벨 렌더러를 사용하며, 리플레이는 기록 시점 상태를 표시한다.

## 제안하는 구현 순서와 완료 기준

1. operation ID·최소 파일 트레이스를 먼저 연결하고 재계획 폭주, 동기 계산, 메모리 할당을 수정한다.
   새 위치 두 곳으로 실제 이동시킨 뒤 명시적 재개, 두 로봇의 단독/동시 주행·교차·장거리·prefer/avoid를 검증한다.
2. 위치 지정의 적용/거절 ACK, 최신 검증 컨텍스트를 보완한다. 동일 좌표 거절과 새 좌표 성공을 구분한다.
3. 환경 checkpoint·파일 인덱스·운용별 내보내기를 완성한다. 프로세스 재시작·맵 이전 뒤에도 같은 ID를 추적한다.
4. 블랙박스 시간 범위 선택·재생·탐색·이벤트 상세·로봇 라벨을 구현한다.

완료 판정에는 다음을 포함한다: 정상 주행의 불필요한 반복 재계획 없음, 계획 중 heartbeat 유지,
취소/운영 제외/맵 변경 뒤 늦은 계획 결과 폐기, 실패마다 operation ID와 단계·이유 조회 가능,
두 로봇·점유·맵 환경의 임의 시각 복원, 손실 구간 표시, 리플레이로 실제 운용 상태가 변경되지 않음.
기록기를 켠 상태의 CPU·메모리·이벤트 루프 지연과 기록량을 함께 측정한다.

기존 PILOT-18 이력·감사 기획과 연결하되, 인증/권한·통합 감사 메뉴까지 이번 범위로 자동 확장하지 않는다.
리플레이 격리 기획은 사용자 추가 요청에 따라 카드로 등록한다.
주행 수정·기록기 등 나머지 구현 후보와 실제 착수 범위·완료 기준은 별도 사용자 검토를 거친다.
