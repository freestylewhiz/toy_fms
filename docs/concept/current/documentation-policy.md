# 문서와 개발 아이템 관리

## 고정 구조

문서는 docs/{concept,fms,web,robot}/{current,backlog,todo}/주제.md 구조를 유지한다.
concept는 통합 방향·공통 개념, fms는 서버, web은 UI, robot은 로봇 구현을 담당한다.
컴포넌트 이름은 코드 디렉터리 이름을 변경하지 않는다.

- current: 실제 코드로 확인한 구현과 확정된 현행 정책. 관련 코드·검증 파일을 연결한다.
- backlog: 미구현 제안, 논의 질문, 대안, 의존성. 우선순위나 구현 방식을 확정 사실로 쓰지 않는다.
- todo: 사용자와 착수를 합의한 범위·완료 기준·관련 Vikunja 카드. 논의 문서를 자동으로 승격하지 않는다.

이번 재구성 시 todo 성격의 미착수 제안은 backlog로 통합했다. 네 todo 디렉터리는 파일 없이 비워 둔다.
Git은 빈 디렉터리를 보존하지 않으므로 새 체크아웃에서는 다음 명령으로 복원한다.

~~~sh
mkdir -p docs/{concept,fms,web,robot}/todo
~~~

## 갱신 규칙

1. 논의는 해당 컴포넌트 backlog에 쓴다. 통합 결정은 concept에 두고 상세 문서에서 연결한다.
2. 사용자와 구현을 합의하면 todo에 범위·완료 기준을 적고 Vikunja 카드와 연결한다.
3. 구현 및 검증 후 current를 실제 동작에 맞게 갱신하고 완료한 todo 문서는 제거한다.
4. backlog에서 해결된 질문은 제거하거나 남은 질문만 유지한다. 같은 내용을 여러 상태에 복제하지 않는다.
5. 정책 변경에는 날짜·이유·영향을 남긴다. 테스트 파일이 있다는 사실과 실제 검증 통과를 구분한다.

Vikunja는 개발 아이템·상태·첨부·검수 대화를 관리하고 docs는 현재 동작·결정·논의의 본문을 관리한다.
**카드**라는 말은 Vikunja에 등록된 개발 아이템을 뜻한다. docs/backlog의 계획 문서는 카드가 아니다.
기획·구현 후보 카드는 개발 승인 전에 등록할 수 있다. 실제 개발은 사용자와 포함 카드·범위·완료 기준을 합의한 뒤 시작한다.
문서 선행 리뷰나 카드 등록 보류를 요청한 경우에는 backlog 문서만 작성하고 카드 등록 요청을 기다린다.
Vikunja 분류는 concept → FMS/planning, fms → FMS/server, web → FMS/web, robot → FMS/robot이다.
Vikunja 카드의 To Do 상태를 docs/todo에 자동 대응시키지 않는다. 논의 카드도 착수 전에는 docs/backlog에 둔다.
카드 변경은 Vikunja UI 또는 REST API로 수행하며, 첨부·스크린샷은 카드에 직접 올린다.

## 카드 라벨과 문서 요약 스냅샷

- 기획·논의 카드에는 `기획`, 구현 카드에는 `구현` 라벨을 붙인다. 두 분류는 카드의 주된 목적을 기준으로 선택한다.
- 구현 후보도 `구현`으로 분류하지만 개발 승인을 뜻하지 않는다. 착수 범위 합의는 별도로 기록한다.
- 구현 카드에는 현재 Project와 같은 라벨(예: `fms/server`, `fms/web`, `fms/robot`)을 추가한다.
  Project가 바뀌면 이전 Project 라벨을 교체한다. 기존 주제 라벨은 유지한다.
- 모든 카드의 description 하단에 아래 형식의 요약을 추가한다. 원문 경로는 워크스페이스 기준으로 명시한다.

~~~text
///////////////
문서 요약 스냅샷
기준일: YYYY-MM-DD (카드 등록 시점)
관련 문서: docs/컴포넌트/backlog/주제.md (저장소 기준 경로)

배경: 이 아이템이 필요한 이유
의도·방향: 해결하려는 문제와 접근 방향
합의 범위·미결정 사항: 등록 당시 확정된 내용과 남은 논의
///////////////
~~~

워크스페이스 Markdown은 논의와 구현에 따라 계속 갱신하는 문서다.
카드의 스냅샷은 등록 시점의 판단을 보존하며, 원문 변경만으로 자동 갱신하거나 덮어쓰지 않는다.
기존 카드에 처음 추가하는 요약은 `(기존 카드 보완 시점)`이라고 표시해 등록 당시 기록과 구분한다.
이후 합의 변경은 날짜·이유·영향을 명시한 추가 기록으로 남기고 카드의 최신 범위·완료 기준도 갱신한다.
새 스냅샷이 필요하면 이전 스냅샷을 보존한 채 날짜가 있는 새 블록을 description 하단에 추가한다.

개발 전에는 카드의 최신 합의·완료 기준과 최신 문서를 함께 확인한다.
스냅샷과 최신 내용이 다르면 변경 기록을 확인하고, 범위나 정책의 충돌이 남으면 사용자와 정리한 뒤 구현한다.
구현 후에는 실제 검증 결과를 카드에 남기고 완료 기준 충족을 확인한 뒤 Review로 옮긴다.
사용자 검토·최종 확인 후 Done으로 확정한다. 검토 중 수정은 In Progress에서 처리하고 다시 Review로 돌린다.
2026-09-17: 사용자 요청으로 검토 단계를 추가했다. 상태 순서는 To Do → In Progress → Review → Done이다.
2026-09-18: 카드 시스템을 Vikunja로 이관하고 동일한 네 상태의 Kanban을 FMS 하위 컴포넌트마다 유지한다.
같은 날 Backlog.md 서비스·이관 원본·복구용 이미지를 제거했다. 새 카드와 상태 변경은 Vikunja에서만 수행한다.

## 심층 논의 식별 코드

심층 논의 문서명은 DISC-NNN-영문주제.md를 사용한다. DISC는 논의 분류, NNN은 저장소 내 고유 번호다.
카드 번호와 분리하며 문서 이동·명칭 변경 시에도 유지한다. 첫 항목은 DISC-001 텔레포터 대기열 관리다.
카드 생성 후에도 신규·기존 카드의 개발 포함 범위를 사용자와 협의하기 전에는 착수하지 않는다.
