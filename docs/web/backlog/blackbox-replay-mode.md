## 사용자 요구와 경계

리플레이 모드의 로봇·경로·점유·트래픽·운용 상태는 **블랙박스에 기록된 데이터만** 반영한다.
라이브 로봇이 이동하거나 새 명령을 받아도 리플레이 화면은 변하지 않아야 한다.
기록이 없거나 읽기에 실패해도 현재 상태로 보충하지 않는다. 과거 명령은 조회 대상이지 실행 대상이 아니다.
실제 로봇과 서버의 운용·기록은 계속되며, 웹의 리플레이 진입 자체는 정지·취소·제어해제를 요청하지 않는다.

2026-09-21 최종 정정: **가능하면 기존 UI 갱신 로직은 변경하지 않고 데이터 소스만 교체한다.**
블랙박스 채널을 만들고 해당 채널에서 수신한 이벤트만 기존 화면 갱신 경로에 전달한다.
라이브 채널과 블랙박스 채널은 기존 UI가 소비하는 동일한 이벤트·상태 계약을 제공한다.
앞선 ‘웹의 라이브 모니터링 데이터 갱신·버퍼링 중단’ 해석은 철회한다. 라이브 수집/캐시의
백그라운드 유지 여부는 이 요구의 핵심도 완료 기준도 아니다. 어떤 선택이든 블랙박스 화면을
갱신할 수 있는 소스는 블랙박스 채널뿐이다. 서버·로봇 운용과 기록은 계속된다.

같은 날 추가 요구: 최근 24시간 이내 기록된 운용 영향 이벤트에서 **시작 이벤트와 끝 이벤트**를
선택해 재생 구간을 정한다. 단순 pose 보고 등 모든 원본 메시지를 선택 후보로 나열하지 않는다.

이번 산출물은 구현을 위한 설계와 검증 기준이다. 주행 결함 수정, 기록기, 조회 API 및 UI 구현은
포함 카드·범위·완료 기준을 별도 합의한 뒤 착수한다. docs/todo로 승격하지 않는다.

## 코드 검토 결과

- `web-client/src/main.ts`의 `snap()`은 `room.state`, 현재 연결 상태, `activeMap`을 직접 조합한다.
  조회 함수 하나만 리플레이용으로 바꾸면 다른 갱신 경로가 남는다.
- `connect()`의 state/ACK/error/leave 콜백이 목록·선택·인스펙터·상태 문구와 캔버스를 직접 변경한다.
  기존 room 일치 검사 외에 화면 세대·모드 검사가 필요하다.
- `scheduleReconnect()`, `loadActiveMap()`의 비동기 완료와 finally, 요청 timeout이 뒤늦게
  연결하거나 화면을 덮어쓸 수 있다. 모드 진입 시 예약 작업과 미완료 요청을 무효화해야 한다.
- `runtimeElapsed()`는 `Date.now()`를 사용한다. 과거 대기 시간도 리플레이 시계로 계산해야 한다.
- 중앙 `send()`에는 리플레이 guard가 없다. 버튼을 비활성화하는 것만으로 명령 전송을 막을 수 없다.

## 상태 소스와 컴포넌트 제안

현재 `operate/scene/VDA` 화면 분류와 별개로 `dataMode`를 둔다. 리플레이 상태가 운용 탭 전환으로 해제되지 않는다.

| 컴포넌트 | 책임 |
| --- | --- |
| LiveEventChannel | 현재 룸의 상태·알림을 기존 UI 계약으로 제공; 비선택 시 화면 갱신 경로와 분리 |
| BlackboxEventChannel | 파일 기록·checkpoint를 같은 UI 이벤트로 변환; 재생 시각 순서로 발행 |
| ChannelSessionController | 화면 갱신 경로에 선택 채널 하나만 연결; 전환 세대와 지연 이벤트 차단 |
| 공통 이벤트 적용기 / SceneStore | 두 채널에 동일한 갱신 로직 적용; 모드 전환 시 상태를 초기화하고 전체 snapshot으로 교체 |
| LiveStore / ReplayStore | 필요 시 데이터 컨텍스트만 격리; 라이브 캐시 유지 여부와 무관하게 화면 소스 혼합 금지 |
| ReplayClock | 선택 시각·일시정지·배속·seek; 재생 경과 시간의 유일한 기준 |
| ActiveSceneSource | 활성 채널이 제공한 snapshot·map assets·clock·읽기 전용 capability를 원자적으로 제공 |
| BlackboxTimeline / EventInspector | 최근 24시간 운용 영향 이벤트에서 시작·끝 선택, 이벤트 상세와 누락 표시 |
| 공통 맵·목록·상세 렌더러 | ActiveSceneSource만 읽음; room·현재 맵·실시간 로봇을 직접 참조하지 않음 |

로봇 위치뿐 아니라 이름·상태·주행 모드 라벨, 경로, 존·예약·대기열, 텔레포터 소속,
운용 목록·상세·상태 문구까지 동일한 소스 경계를 적용한다. 카메라·확대·선택·레이어 조작은 로컬 UI 상태다.
기록 당시 로봇 연결 상태를 현재 브라우저 연결 여부로 덮어쓰지 않는다.

공통 흐름은 `선택된 이벤트 채널 → 공통 이벤트 적용기 → 화면 상태 → 기존 화면 갱신·렌더링`이다.
리플레이용 지도·목록·상세 갱신기를 따로 복제하지 않는다. 현재 콜백 안에 섞인 상태 적용·화면 갱신과
통신/명령 부작용은 경계를 분리하되, 표시 규칙과 렌더러는 두 채널이 공유한다.
기존 UI가 받는 계약에 맞추는 책임은 채널 어댑터에 둔다. 재생 때문에 개별 UI 갱신 함수에
모드별 분기를 추가하지 않는 것을 우선한다. 필요한 최소 변경은 채널 연결 지점·시계 주입·
운용 송신 안전 경계에 한정해 검토하고, 불가피한 UI 변경은 이유와 영향 범위를 별도 확인한다.

공통 채널 인터페이스 제안은 `subscribe(handler) / unsubscribe() / dispose()`와 초기 전체 snapshot이다.
이벤트 envelope에는 `channelKind`, `channelSessionId`, `generation`, `sequence`, `eventId`,
`eventTime`, `mapId`, `mapRevision`, `type`, `payload`를 둔다. 상태 초기화/전체 교체·상태 변경·알림·
자산/시계 컨텍스트를 공통 계약으로 전달하고 적용 직전에 활성 세션·세대·순서·맵을 확인한다.
seek와 맵 변경은 세대를 교체한 뒤 새 전체 상태를 발행하여 이전 위치·객체가 남지 않게 한다.
운용 전송은 이벤트 수신 인터페이스와 별개이며, 공통 이벤트 적용기는 외부 쓰기를 수행하지 않는다.
채널은 논리적 수신 소스 계약이다. 별도 WebSocket/서버 룸을 사용할지, 조회한 기록을 웹에서
발행할지는 후속 전송 방식 결정이며, 어떤 방식이든 활성 채널 외의 이벤트 적용은 금지한다.

## 모드 전환과 비동기 격리

| 상태 | 표시 데이터 | 운용·편집 전송 |
| --- | --- | --- |
| live | 최신 라이브 상태 | 기존 운영 정책과 연결·동기화 조건 충족 시 가능 |
| replay-loading | 기록 로딩 화면; 라이브 객체 표시 안 함 | 불가 |
| replay-paused / replay-playing | 기록으로 복원한 상태만 | 불가 |
| replay-error | 기록 오류·공백; 마지막 유효 기록은 시각·stale 표시와 함께 제공 가능 | 불가 |
| live-resync | 복귀 로딩 화면; 기록/현재 상태 혼합 금지 | 불가 |

진입 순서 제안:

1. 미저장 편집은 폐기 확인을 받고 취소 시 live를 유지한다. 저장·운용 요청이 미응답이면
   실제 요청은 계속될 수 있음을 안내하며, 진입이 해당 요청을 취소하거나 재전송하지 않는다.
2. 전송을 먼저 잠그고 view generation을 증가시킨다. 라이브 UI 선택·초안·timeout·재접속 예약을 해제한다.
3. 화면 갱신 경로의 라이브 채널 연결을 해제하고 블랙박스 채널로 교체한다.
   라이브 전송 연결 종료나 LiveStore 동결 자체를 필수 조건으로 두지 않는다.
   로봇 gRPC/FMS/기록기는 유지한다. 늦은 ACK, leave/error, join 완료, 맵 fetch 완료는
   선택 채널과 generation이 일치하지 않으면 화면을 갱신하지 않는다.
4. 블랙박스 채널에서 기록 자산·checkpoint·이벤트로 초기 전체 상태를 발행하고,
   공통 갱신 경로로 한 번에 공개한 뒤 paused 상태로 시작한다.
   종료된 구독만 믿지 않고 모든 callback과 finally까지 세대 검사를 적용한다.

라이브 수집·캐시를 유지하더라도 화면에서는 직접 참조하지 않는다. 라이브 이벤트·ACK·단절 알림·
재접속 결과가 공통 화면 갱신 경로에 우회 진입하지 못하도록 채널 경계에서 차단한다.
합격 기준은 비활성 데이터 저장소의 변경 여부가 아니라 **화면에 적용된 이벤트의 채널 출처**다.

복귀는 사용자가 명시적으로 요청한다. 블랙박스 채널을 해제하고 replay 작업을 무효화한다.
새 라이브 채널의 연결·최신 전체 snapshot·현재
자산이 같은 맵으로 준비된 후 화면을 교체한다. 재생 중 쌓인 delta나 이전 pending 명령을 적용·자동 송신하지 않는다.
그 뒤에도 운영 제외·단절 등 기존 로봇별 제어 조건을 충족해야 운용이 가능하다.
연결 실패 시 live-resync 오류로 남아 제어를 잠그며, 재시도 또는 리플레이로 돌아가기만 제공한다.

## 재생 데이터 계약과 시각 일관성

- 당시 맵 ID/revision, 자산 해시, 전체 맵 checkpoint, 순서가 정해진 상태 이벤트와
  operation 참조를 조회 API에서 제공해야 한다. 현재 서버 맵·정의로 대체하지 않는다.
- checkpoint에는 반영 완료한 stream별 sequence 경계와 환경 revision을 포함한다.
  그 이후 이벤트만 중복 제거해 적용한다. 같은 원인에 대한 프로토콜 송수신 기록은 진단용이고,
  화면에는 정규화된 상태 이벤트를 한 번만 적용한다. eventId로 재적용을 방지한다.
- 프로세스 간 기록의 시간 차이와 인과 순서를 조회 계층에서 정규화한다. 벽시계 정렬만으로
  텔레포터의 출발·도착 소유권을 추정하지 않는다. 확정할 수 없는 구간은 불확실성으로 표시한다.
- 시간 범위 시작 직전의 유효 checkpoint부터 커서까지 적용한다. 뒤로 seek하면 새로 복원한다.
  seek/map 변경마다 별도 generation을 증가시켜 늦게 끝난 이전 조회 결과를 버린다.
- operation/로봇 필터는 강조·상세 범위를 줄이는 기능이다. 주변 로봇·점유·환경 이벤트를 제거해
  전체 맵의 재현 상태를 왜곡하지 않는다. 맵 전환은 같은 재생 시각을 유지하며 기록 자산만 로드한다.
- 선택 맵에 로봇이 입장·퇴장한 기록으로 소속을 구성한다. 다른 맵에 같은 로봇이 중복 표시되지 않아야 한다.
- 재생 경과 시간·대기 시간·lastSeen 표시·이벤트 애니메이션은 ReplayClock을 따른다.
  재생 속도 제어에는 로컬 monotonic 시간을 사용할 수 있으나 정지 중 커서와 과거 상태는 변하지 않는다.
- 자산 누락·기록 손실·스키마 미지원은 명시적 오류/공백이다. 마지막 유효 값을 정상 현재 상태처럼
  계속 표시하지 않고, 누락 구간을 통과한 상태는 다음 유효 checkpoint 등으로 복원될 때까지 불완전 표시한다.
  텔레포트·테스트 위치 지정·단절·누락 구간을 보간하지 않는다.

기록기·조회 API·과거 자산이 선행 의존성이다. 기존 stdout과 최신 위치 journal만으로 과거 주행을
완전 복원할 수 없다. UI 격리는 fixture로 선행 검증할 수 있지만 실제 기록 연동을 완료로 간주하지 않는다.

## UI·전송 안전성

- 상시 `블랙박스 · 리플레이 · 읽기 전용` 표시와 기록 시각(명시적 시간대)을 제공한다.
  실제 로봇은 계속 운용 중이라는 안내와 명시적 `라이브로 돌아가기` 버튼을 둔다.
- 하단 가로 타임라인에서 최근 24시간의 운용 영향 이벤트를 시작/끝으로 선택한다.
  운용 구간 막대, 이벤트 마커, operation ID와 원인 상세를 제공한다. 범위 끝에서는 정지하며
  라이브로 자동 전환하지 않는다. 자유로운 시각 입력만으로 이벤트 선택을 대체하지 않는다.
- 리플레이 화면의 운용·테스트 위치 지정·점유 해제·제어 전환·맵/리소스 저장·삭제를 모두 잠근다.
  테스트 위치 지정은 **라이브의 운영 제외 상태에서는 가능**하지만 **리플레이에서는 불가**다.
- 키보드·문맥 메뉴·진입 전에 열린 확인창·오래된 callback을 포함해 중앙 전송 경계에서 차단한다.
  확인창 승인 뒤에도 최신 모드를 다시 검사한다. 차단된 요청을 큐에 저장하거나 복귀 후 재전송하지 않는다.
- 두 채널의 공통 이벤트 적용기는 기록된 명령·ACK도 화면 자료로만 해석한다.
  기존 live 핸들러의 통신 부작용·send 함수는 호출하지 않으며, 분리한 공통 화면 갱신 함수만 재사용한다.
  향후 추가될 HTTP 쓰기 경로도 같은 capability 검사를 사용한다.

## 최근 24시간의 시작·끝 이벤트 선택

선택 후보는 현재 선택 맵에 영향을 준 **운용 명령, 오류 상태로의 변화, 강제 상태전환 등
운용환경에 영향을 미치는 이벤트**다. 선택 목록과 실제 재생 스트림은 구분한다.

| 선택 후보 분류 | 예시·분류 기준 |
| --- | --- |
| 운용 명령 | move/dock/cancel/텔레포터 운용 등의 요청 및 결과. 같은 operationId로 묶고 단계 구분 |
| 오류 상태 변화 | 로봇의 오류 진입, 명령 실패·중단, 제어 동기화 실패 등 오류로의 전이. 동일 오류의 반복 보고는 하나의 사건으로 묶음 |
| 강제 상태전환 | 운영 제외/재개, 강제 점유 해제, 테스트 위치 지정 등 운영자가 수행한 상태 변경 |
| 기타 운용 영향 | 맵 소속 이전, 운용에 영향을 준 연결 단절·복구, 트래픽 강제 개입, 환경/리소스 변경 등. 세부 포함 eventType은 후속 합의 |

정상 주기 pose·heartbeat·동일 상태 반복 보고·일반 경로 점은 시작/끝 선택 후보에서 제외한다.
운용 요청이 거절된 경우도 명령 사건으로 조회할 수 있지만 실제 상태 변경이 있었던 것처럼 표시하지 않는다.

선택·조회 계약 제안:

1. 조회 기준 시각 `asOf`(서버 UTC)를 고정하고 `[asOf - 24시간, asOf]`에 속한 기록 이벤트를
   현재 맵 영향 기준으로 조회한다. UI는 시간대를 표시한다. 새 이벤트로 후보를 갱신하더라도
   이미 선택한 경계가 자동 이동하지 않으며 명시적 새로고침 때 유효성을 재검사한다.
2. 후보에는 eventId·발생 시각·유형·로봇·맵·operationId·단계/결과·사유를 표시한다.
   한 사건의 프로토콜 송신/수신 중복은 별도 후보로 부풀리지 않는다. 시간 동률은 기록 순서 키로 구분한다.
3. 가로 타임라인 마커 또는 목록에서 `시작으로 지정` / `끝으로 지정`한다. 핸들은 후보 이벤트에
   스냅하며 선택 이벤트의 상세를 확인할 수 있다. 상태는 `startEventId`, `endEventId`와 시간·순서 키로 보존한다.
4. 시작이 끝보다 늦으면 재생을 허용하지 않는다. 양 끝 이벤트를 포함하며, 같은 이벤트를 선택한 경우
   단일 사건 스텝으로 조회하는 방안을 제안한다. 시작/끝이 동일 operation일 필요는 없다.
5. 시작 이전 checkpoint에서 시작 직전 상태를 복원한 후 시작 이벤트부터 끝 이벤트까지 적용한다.
   복원에 필요한 checkpoint는 24시간보다 오래될 수 있다. 선택 가능 기간 24시간을 로그 보존 기간으로 해석하지 않는다.
6. 실제 재생에는 선택한 두 사건 **사이의 전체 맵 재현에 필요한 pose·경로·점유·상태·환경 이벤트**를
   포함한다. 선택 후보 이벤트만 재생해서 중간 주행과 주변 로봇 맥락이 사라져서는 안 된다.
7. 후보 없음, 로그 만료, 자산/초기 상태 누락은 명시적으로 표시한다. 맵 변경 시 선택 사건이 새 맵에
   영향을 주는지 재검사하고 유효하지 않으면 재선택을 요청한다. 현재 상태나 임의 다른 사건으로 대체하지 않는다.

파일 인덱스/조회 API는 24시간·영향 맵·분류별 후보 검색 및 페이지 이동과 eventId 경계 기반 재생 조회를 지원해야 한다.
선택 이벤트 조회와 재생 데이터 조회는 같은 기록 버전/순서 기준을 사용한다. 서버 보존 정책과 상세 분류표는 별도 결정한다.

## 구현 시 필수 완료 기준

1. 같은 robotId를 기록/라이브에 두고 라이브 pose·상태·맵·점유를 변경해도 모든 리플레이 패널이 변하지 않는다.
2. 진입 직전/직후의 state, ACK, error, leave, reconnect, timeout 및 늦은 자산 응답을 주입해도
   화면 오염·리플레이 선택 해제·표시 소스의 라이브 전환이 없다.
3. 버튼·단축키·문맥 메뉴·미리 열린 확인창·중앙 dispatcher 직접 호출로 리플레이 및 전환 상태에서
   시도한 운용/편집 송신이 0건이다. 기록 명령 재생도 실제 명령을 송신하지 않는다.
4. 일시정지 중 실제 시간이 지나도 pose·경로·대기 시간·연결 표시가 바뀌지 않는다.
   같은 커서의 순차 재생과 checkpoint+seek 결과가 일치한다.
5. 두 로봇과 yard/large_lab fixture로 텔레포트·위치 지정·운영 제외/재개·점유 변화를 재생한다.
   뒤로/앞으로 빠른 seek, 맵 연속 변경에서 오래된 요청이 마지막 선택을 덮어쓰지 않는다.
6. 자산 누락·로그 손실·checkpoint 부재·미지원 스키마·조회 실패 시 라이브 fallback이 없고 오류/공백을 표시한다.
7. 복귀 성공 시 최신 전체 상태가 표시되며 이전 명령을 재전송하지 않는다. 실패 중에는 제어가 계속 잠긴다.
8. 리플레이 진입·종료 자체가 실제 로봇 상태·명령·점유를 변경하지 않고, 별도 FMS 기록은 지속된다.
9. 블랙박스 모드에서 공통 화면 갱신 경로에 적용된 이벤트는 모두 선택한 블랙박스 채널에서 온 것이다.
   라이브 수집/캐시 갱신을 병행해도 이 기준을 만족하며, 라이브 저장소 동결 여부로 합격을 판단하지 않는다.
10. 동일한 정규화 이벤트 시퀀스를 각각 라이브/블랙박스 채널 fixture로 전달했을 때 공통 상태 적용·
    화면 갱신 경로와 표시 결과가 동일하다. 채널 메타데이터·읽기 전용 권한·시계 기준 차이는 구분한다.
11. 최근 24시간 경계 안의 운용 명령·오류 전이·강제 상태전환만 해당 분류의 선택 후보가 되며,
    정상 pose/heartbeat는 후보가 아니다. 빈 목록·시간 동률·역순 선택·새로고침·맵 변경을 검증한다.
12. 시작/끝 eventId를 지정하면 양 끝과 중간 주행·주변 로봇·점유 변화까지 재생한다.
    24시간 이전 checkpoint로 초기 상태를 복원하는 경우와 기록 누락·만료 시 오류 표시를 검증한다.
