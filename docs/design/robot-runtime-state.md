# 로봇 런타임 상태·점유 복구·주행 방식 설계 기록

- 문서 ID: `DESIGN-ROBOT-RUNTIME-001`
- 개정: `0.2` / 2026-09-15
- 상태: **초기 구현 완료 — 후속 주행 모드 확장 항목은 별도 관리**
- 목적: 다음 구현과 향후 트래픽 제어 모드 추가 시 이번 논의의 의도와 경계를 보존한다.
- 현재 구현 설명: [robot-state-sync.md](../robot-state-sync.md)

이 문서는 설계 결정의 기준이다. 공통 상태 필드·enum의 코드 정본은
[`shared/robotRuntime.ts`](../../shared/robotRuntime.ts)이다. 향후 주행 모드 관련 내용은
확장 경계이며 구현 완료를 의미하지 않는다. 변경 이유와 영향을 아래 이력에 남긴다.
사용자의 최신 지시를 우선한다.

점유를 수동 복구하고, 오래된 보고나 재접속으로 운영·점유가 되살아나는 것을 방지한다.

## 3. 상태 모델

| 필드 | 값 | 의미/소유권 |
| --- | --- | --- |
| `workState` | `idle / busy / unknown` | 작업 없음 / 미종료 작업 있음 / 최신 상태 확인 불가 |
| `fmsControlState` | `enabled / disabled` | 사용자 운영 참여 설정. DB 보존 |
| `connectionState` | `online / offline` | 통신 계층이 판단하는 연결 상태 |
| `connectionReason` | 정상 종료·timeout 등 원인 코드 | 연결이 끊긴 이유. enum은 미확정 |
| `driveState` | `stationary / moving / waiting / paused / blocked / unknown` | 현재 주행 상태의 UI 투영 |
| `driveContext` | 원인 코드·출처·대상·차단 로봇·요청 ID·시각 | 정지/대기의 근거. 복수 원인을 수용할 구조 필요 |

### 의미와 전이 원칙

- corridor 대기 중인 미종료 작업은 `busy`이다. 정차 적재/하역도 `busy + stationary`일 수 있다.
- `moving`은 차체 이동과 제자리 회전을 포함한다. FMS의 이동 허가 자체가 실제 이동을 뜻하지 않는다.
- `waiting`은 점유·허가·선행 액션 등을 기다리는 절차상 대기, `paused`는 명시적 일시정지,
  `blocked`는 안전장치·장애물·오류 등에 따른 주행 불가로 구분한다.
- `stationary`는 확인된 정지이며 `unknown`은 보고가 없거나 오래되어 확인 불가인 상태다.
- 실제 보고와 FMS 결정을 분리한다. 운영 제외/정지 요청을 했다고 실제 주행을 정지로 덮어쓰지 않는다.
- `disabled + online + moving`도 가능하다. 이 경우 운영 제외와 관측된 움직임을 함께 보여준다.
- 통신 두절만으로 `disabled`로 바꾸지 않는다. 마지막 보고는 보존하고 현재 작업·주행 상태는 unknown으로 투영한다.
- 허가/정지 명령의 전송·수락·실제 동작 확인을 구분한다. 허가만으로 moving을 표시하지 않는다.
- 작업의 완료·취소·실패는 명령 생명주기에서 다룬다. 기존 `motion`, `trafficStatus`, `commandState`는
  의미를 분석해 새 필드로 투영하며 한 번에 문자열 치환하지 않는다.

### 대기 사유

`resource_occupied`, `permission_pending`, `traffic_yield`, `route_update_pending`,
`action_in_progress`, `operator_pause`, `obstacle_detected`, `safety_stop`,
`localization_error`, `control_unavailable`.

이 코드는 자체 FMS 정의이며 VDA 표준 enum이 아니다. 원인 목록은 `driveContextJson`에
배열로 전달한다. 로봇 관측 원인과 서버의 점유 판단을 분리해 함께 보여준다.

```ts
// 단일 대기 원인의 예시. 실제 driveContext는 이 객체들의 배열이다.
driveContext: [{
  reasonCode: "resource_occupied",
  source: "fms",
  target: { mapId: "yard", kind: "zone", id: "drive-corridor" },
  blockingRobotIds: ["robot-1"],
  requestId: "access-123",
  permissionState: "queued",
  since: 1789441200000 // Unix epoch milliseconds
}]
```

판정은 코드·ID에 기반하고 표시 이름은 조회한다. 점유 로봇은 실제 점유·예약 데이터에서 가져온다.
복수 원인은 내부에 유지하고 지도에 대표 원인, 상세 패널에 전체 원인을 표시하는 방향이다.

## 4. 보고 신선도와 제어 세대

구현 메타데이터: `reportedAt`, `stateChangedAt`, `sessionId`, `controlEpoch`. 서버 수신 시각은 기존 `lastSeenAt`을 사용한다.

- 로봇 보고 시각과 서버 수신 시각을 구분한다. 시계 오차가 있으므로 신선도 기준은 별도 결정한다.
- 새로운 세션/제어 세대 이전의 메시지가 현재 명령·점유를 복원하지 않게 한다.
- `controlEpoch`는 명령/예약의 유효 세대 후보이며 `sessionId`와 같은 의미가 아니다.
- 운영 제외 후에도 관측 텔레메트리를 수신할 수 있지만 운영 제어의 승인으로 해석하지 않는다.

## 5. 영속 점유와 수동 복구

점유 데이터:

- 공통 `resourceRef: { mapId, kind, id }`, `robotId`
- `reserved / occupied` 구분, 요청 ID와 제어 세대
- 생성·갱신·해제 시각, 해제 사유, 처리 사용자
- 필요 시 리소스/그래프 버전 또는 경로 단계 참조

초기에는 zone 점유만 구현하되 저장 구조를 `zoneId` 전용으로 고정하지 않는다.
대기열도 영속화한다. 로봇의 몸체와 가까운 경로를 기준으로 예약→실점유 및 정상 해제를 판단한다. 오프라인·제어 동기화 전·운영 제외 보유자는 명시적 복구 전까지 유지한다.

구현한 수동 복구 절차:

1. 사용자가 점유/예약과 로봇을 선택하고 확인한다.
2. 로봇의 `disabled` 전환과 선택한 점유 해제를 같은 DB 트랜잭션에 기록한다.
3. UI와 메모리 투영을 갱신하고 이전 세대의 허가·요청을 무효화한다.
4. 다른 리소스에 남은 점유는 표시한다. 사용자가 선택하지 않은 점유까지 암묵적으로 전부 해제하지 않는다.
5. 사용자가 운영 재개를 요청하면 연결·현재 위치·작업·점유 동기화를 확인한 뒤 enabled로 전환한다.
   실패하면 disabled를 유지한다. 과거 작업은 자동 재개하지 않는다.

유지해야 할 경계:

- DB 트랜잭션은 로봇이 물리적으로 정지/이동했음을 보장하지 않는다.
- 운영 제외 로봇을 예약·허가에는 참여시키지 않되, 최신 위치가 실제 장애물로 관측되는 경우의
  충돌 회피 정책까지 함께 무효화해서는 안 된다. 수동 해제와 물리적 존재의 취급을 구분해 설계한다.
- 정지·취소·세션 종료·상태 동기화 등 운영 제외 상태에서 허용할 제어 메시지는 별도 확정한다.
- 재시작 시 DB 복원과 미확인 실제 위치의 조정, 중복 해제/활성화의 멱등성을 검토한다.

## 6. 주행 방식과 경로 표현의 확장 경계

자유 주행/그래프 주행은 현재 움직임(driveState)과 다른 축이다. 노드·엣지 경로를 받아
로봇이 구간 내부를 자율 계획할 수 있으므로 자율성과 그래프 사용을 반대 개념으로 두지 않는다.

| 필드 | 제안 값 |
| --- | --- |
| `navigationMode` | `free_navigation / graph_navigation / unknown` |
| `pathPlanningAuthority` | `robot / fms / hybrid / unknown` |

구분할 적용 단위:

1. 로봇 능력: 지원 가능한 주행 방식 목록
2. 작업 설정: 이번 작업에 요청한 방식
3. 실행 상태: 실제 적용 중인 방식

경로 표현의 공통 정보는 `routeId`, `routeRevision`, `mapId`, `mapVersion`을 후보로 둔다.
그래프 경로에는 `graphId`, `graphVersion`, 순서 있는 노드/엣지 steps가 필요하다.
같은 리소스를 여러 번 지날 수 있으므로 각 단계에 `stepId` 또는 `sequence`를 둔다.
자유 주행의 목적지·경유점·계획 경로와 그래프 경로를 구별하고, 로봇의 실제 단기 경로
`localPath`는 두 방식 모두에서 함께 존재할 수 있게 한다.

점유/대기 대상은 zone 외 node/edge 및 필요 시 경로 step으로 확장할 수 있어야 한다.
이는 표현의 확장 경계이며 방향별 엣지 통행·구간 예약 알고리즘이 구현되었다는 뜻이 아니다.

주행 방식 전환은 초기에는 작업이 없고 정지했을 때 허용하는 방향을 제안했다.
주행 중 전환, 복수 계획 주체, 추가 트래픽 모드의 정확한 제약은 미결정이다.
`navigationMode`와 교통 중재 정책(traffic policy ID)도 같은 필드로 합치지 않는다.

## 7. UI 기획 방향

- 로봇 외곽 링: 정상 운영 / 통신 두절 / 운영 제외. 색 외에 점선·기호도 사용한다.
- 작은 작업 배지: 대기 / 작업 중 / 확인 불가.
- 아이콘 아래 문구: 주행 중 / 점유 대기 / 일시정지 / 주행 불가.
- 상세 패널: 원인·제어 대상·차단 로봇·허가 상태·대기 시간·마지막 보고 시각.
- 구역 런타임 영역: 실제 점유·진입 예약·대기열을 구별하고 선택 대상의 수동 해제 기능 제공.

예: `작업 중 · 점유 대기 · 복도 A / robot-1 점유 / 12초 대기`.
레이아웃과 시각 표현은 구현 시 실제 정보량을 검수해 조정한다.

## 8. VDA 검토는 미래 참고용

현재 VDA 통신 구현이나 완전 호환을 요청받은 것이 아니다. 향후 별도 운영 모드/어댑터에서
프로토콜 원본을 보존하고 내부 모델로 변환한다. 검토 기준은 VDA 5050 3.0.0이었다.

- `fmsControlState`는 사용자 운영 정책이고 로봇이 보고하는 `operatingMode`와 다르다.
- `driving=false`만으로 idle/작업 완료/점유 대기를 단정하지 않는다.
- 자체 corridor polygon 정원 제어와 표준의 edge corridor 개념을 혼동하지 않는다.
- VDA 전용 연결 상태/요청 필드를 지금 모두 추가하지 않는다.
- 실제 어댑터 작업 때 적용 버전의 공식 사양을 다시 확인한다.

참고: https://github.com/VDA5050/VDA5050/blob/3.0.0/VDA5050_EN.md

## 9. 구현에서 정한 사항과 남은 결정

확정·구현:

- 상태 어휘는 shared/robotRuntime.ts. 로봇 관측 원인과 FMS 점유 원인은 배열로 합친다.
- 구역의 실제 점유·예약·FIFO 대기열을 DB에 저장한다. 오프라인 대기자는 유지하되 허가는 하지 않는다.
- 선택한 점유만 수동 해제하고 해당 로봇을 운영 제외한다. 다른 보유는 유지한다.
- 제어 세대·스트림 세션을 검증하며 정상 명령은 enabled + controlReady + 최신 연결에서만 처리한다.
- 운영 제외 중 telemetry는 수신한다. 제어 상태 통지·취소·지도 스냅샷은 허용하고 정상 트래픽 참여는 차단한다.
- 활성화 확인 중 DB는 disabled를 유지한다. 최신 pose → ACK 순서와 idle/정지 검증 후 enabled로 확정한다.
- 운영 정책은 즉시 저장, 위치 보고는 최대 1초 단위 저장. 신규 세션은 과거 작업을 자동 재개하지 않는다.
- UI 처리자 감사 정보는 클라이언트 세션 ID다. 인증된 사용자 계정 모델은 이번에 추가하지 않았다.

후속 결정:

- 그래프 노드·엣지·방향별 예약과 반복 경로 단계, 그래프 버전 관리
- capabilities / requested / current navigation 모드의 상세 스키마와 주행 중 전환 정책
- VDA 운영 모드·공식 버전별 어댑터
- 실제 로봇 센서 기반 오프라인 장애물 해소 정책, 인증된 운영자 계정 및 영구 명령 이력

## 10. 구현 시 검증할 대표 시나리오

- 서버 재시작 후 점유 복원, 오프라인 점유자 때문에 신규 진입 제한
- 수동 해제와 운영 제외의 원자성, 중복 요청과 동시에 들어온 보고 처리
- disabled 로봇의 텔레메트리 표시와 명령·예약 차단
- 오래된 세션/세대의 메시지로 점유·운영이 부활하지 않음
- 사용자 재활성화 성공·실패 및 이전 작업 재실행 방지
- 점유 대기 busy, 실제 이동 확인, 통신 두절 unknown, 복수 대기 원인 표시
- 동일 그래프 노드/엣지 반복 통과를 경로 단계로 식별할 수 있음
