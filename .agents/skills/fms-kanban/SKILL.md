# FMS 칸반 작업

## 정본과 접속

현재 체크아웃 루트의 [AGENTS.md](../../../AGENTS.md)와
[문서 운영 정책](../../../docs/concept/current/documentation-policy.md)을 읽는다.
이미 읽은 내용은 다시 읽지 않아도 된다. 사용자 최신 합의가 우선한다.
Vikunja는 카드·상태·첨부·검수 대화의 정본, `docs/`는 현재 정책과 논의 본문의 정본이다.
GitHub Issues나 과거 Backlog.md로 임의 대체하지 않는다.

새 PC에서는 [연결 안내](../../../docs/concept/current/agent-workflow.md)를 따른다.
`VIKUNJA_URL`과 별도 `VIKUNJA_API_TOKEN`으로 접속한다. 토큰을 출력하거나 Git에 넣지 않는다.
UI 또는 REST API를 사용한다. 특정 MCP가 설치되어 있다고 가정하지 않는다.
REST API를 사용할 때 [호출 절차](references/vikunja-api.md)를 읽는다.

## 작업 흐름

1. 요청한 카드의 최신 description, 댓글, 라벨, 프로젝트, 칸반 상태와 연결된 docs를 확인한다.
   표시 코드(예: `PILOT-13`)와 API의 숫자 `id`는 다르다. 숫자 접미사를 task ID로 사용하지 않는다.
2. 프로젝트를 아래 매핑으로 찾는다. 실제 프로젝트·view·bucket·label ID를 조회하며 과거 ID를 재사용하지 않는다.
   조회 결과가 여러 페이지면 전부 확인한다. 중복 후보가 있으면 제목과 본문·프로젝트로 구분한다.
3. 카드 생성 요청이면 기존 유사 카드를 먼저 확인한다. 개발 승인 전 후보 카드 등록은 가능하다.
   사용자가 문서 논의만 요청했거나 카드 등록 보류를 지시했다면 해당 `docs/.../backlog`만 갱신한다.
4. 구현은 사용자와 포함 카드·범위·완료 기준을 합의한 경우 진행한다. 현재 대화에서 이미 승인했다면
   같은 승인을 다시 요구하지 않는다. 카드의 `To Do` 상태나 `구현` 라벨만으로 착수하지 않는다.
5. 승인된 구현을 시작하면 `In Progress`, 구현·검증을 마치면 근거와 함께 `Review`로 이동한다.
   검수 중 수정 요청은 `In Progress` → 수정·재검증 → `Review`다.
   사용자 최종 확인이 있을 때만 `Done`으로 이동하고 완료 처리한다.
6. 구현 후 해당 `current` 문서를 갱신하고 완료한 `todo` 및 해결된 `backlog`를 정리한다.
   결과에는 카드 링크·표시 코드·상태, 변경 문서, 검증 근거, 남은 항목을 기록한다.

| docs 컴포넌트 | Vikunja 프로젝트 경로 | 구현 카드의 프로젝트 라벨 |
| --- | --- | --- |
| concept | FMS/planning | fms/planning |
| fms | FMS/server | fms/server |
| web | FMS/web | fms/web |
| robot | FMS/robot | fms/robot |

프로젝트 경로는 부모 FMS와 하위 프로젝트 이름으로 확인한다. 성격 라벨은 `기획` 또는 `구현`이며,
기존 주제 라벨은 보존한다. 구현 카드의 프로젝트 변경 시 이전 프로젝트 라벨만 교체한다.
라벨의 실제 대소문자·명칭은 서버에서 확인하고, 없을 때 같은 뜻의 라벨을 중복 생성하지 않는다.

## 카드 본문과 검증 기록

- description 하단에 `///////////////`로 감싼 문서 요약 스냅샷을 넣는다.
  [정본 템플릿](../../../docs/concept/current/documentation-policy.md#카드-라벨과-문서-요약-스냅샷)을 사용한다.
  기준일, 저장소 기준 문서 경로, 배경, 의도, 합의 범위, 미결정 사항을 남긴다.
- 기존 스냅샷은 보존하고 변경 합의는 날짜가 있는 추가 기록으로 남긴다. 기존 카드 보완은 보완 시점임을 명시한다.
- 검증 결과에는 실행 명령, 결과, 코드 커밋(있으면), 문서 경로와 남은 한계를 쓴다.
  필요한 로그·화면은 카드에 첨부한다. 다른 PC에서 읽을 수 없는 `/tmp/...` 경로만을 영구 근거로 삼지 않는다.
- 사용자 요청과 기존 합의 범위의 카드 갱신은 수행하되 이 스킬 자체를 무관한 카드 변경·댓글 발송의 승인으로 삼지 않는다.

## API 실패와 완료 판단

쓰기 전 최신 객체를 읽고 기존 본문·라벨·담당자·일정을 보존한다. 적용 후 다시 조회해 확인한다.
특히 `Review`를 완료 체크와 혼동하지 않는다. kanban view의 `done_bucket_id` 이동은
`done=true`를 유발할 수 있으므로 사용자 최종 확인 전에는 사용하지 않는다.

연결 실패·401·403이면 관련 네트워크나 사용자별 토큰/권한만 확인을 요청한다.
서버 DB 직접 편집이나 로컬 문서만으로 카드 변경 성공을 대신하지 않는다.
쓰기 timeout은 결과를 다시 읽어 적용 여부를 확인한 뒤 재시도한다. 생성·댓글·첨부를 맹목적으로 반복하지 않는다.
접속이 막혀도 승인된 로컬 작업은 가능한 범위에서 진행하고, 미반영 카드 변경은 결과에 명시한다.
